# 经典同步问题
【信号量】表示一类资源的余量，这里wait()等待到其有余量的时候取走一个，signal()释放一个资源；考虑哪些地方需要等待
## bounded-buffer problem
producer和consumer共同使用大小为n的一个buffer；需要保证producer不能再buffer满了的时候放数据，consumer不能在buffer空了的时候拿数据
可能会有死锁，因为可能会拿着锁互相等。解决方案就是不要拿着锁等就好了，如果不满足条件就直接释放掉
- 开始只有一个信号量，这会造成一点问题（循环等待？）
- 于是增加成两个信号量，因为一个代表空的格子供给producer，一个代表有东西的格子供给consumer
## readers-writers problem
有读的时候其他进程也可以读；有写的时候不能有其他读和其他写
演化过程：
- 最开始设计了两个锁W和R
- 调整了一下程序变成另一个等价程序
- 调整了一下R和W的顺序因为不能死锁啊
- 发现R和W其实是同一个锁，统一命名为writer-lock
这种情况下可能reader优先级会比writer高，因为有reader就可以进去读了，这样写进程可能会饿死
那么写进程如果ready其他的读进程应该等待，分配一个优先级；新增一个信号量来实现
## Dining-Philosophers Problem
- 一种朴素的想法是先拿左边的再拿右边的，然后就死锁了，因为可能所有人都拿到了同一边的筷子然后都吃不上饭
- 更换成只能同时拿起两根筷子：那么就不会死锁，因为所有人要么在拿筷子要么在等别的锁释放，拿到筷子的人最终都会吃完饭，这样就等锁的人就等到了
- 也可能是：奇数的人拿左边；偶数的人拿右边
	破坏了死锁

# 死锁
【死锁】多个进程竞争资源导致的一种僵局；同时等待对方释放持有的资源
～窄路会车 可能就堵死了 starvation
- 优先级队列来解决 等得越久优先级越高
【系统资源分配图】刻画系统资源的情况；系统的某一个状态
	- 方块表示资源
	- 黑点表示资源实例
	- 圆圈表示进程
	- 黑边表示分配：圆圈指向表示想要；指向圆圈表示持有
- 当前系统分配图里无环一定没有死锁；有环可能有死锁也可能没有死锁（因为可能有多个实例，如果有实例被释放了就可以继续顺畅进行，死锁解散）；如果每个资源只有一个实例并且有环的时候必定死锁（只有一个放不出来啊！）

3. 资源不能被抢占，只能是被主动释放的
4. 有一组等待进程{}并且成环

## 死锁预防
- 破坏先决条件
1. 美好地希望所有的资源都可以共享
2. 保证每个进程在申请资源的时候不能占有其他资源 但是这样资源利用率有点低
3. 保证每个进程在申请资源失败的时候就释放掉正在拥有的其他资源，直到所有的资源都可获得才执行当前的进程
4. 对所有的资源类型进行排序，智能按照固定的顺序申请资源
	但是可能程序员不按照这个顺序来，就还是会死锁；可能会影响资源利用率
## 死锁避免
如果分配这一个资源会导致死锁就不分配：考虑是否让这个请求等待从而避免有可能出现的死锁
【资源分配状态】
- 最大需求
- 当前系统的available和allocated的资源数目
【资源分配图算法】如果每个资源只有一种实例 时可以用；一个可能的需求用虚线，真的出现的时候变成实线，资源释放的时候重新变回虚线，如果一个request edge转变成assignment edge不会让图中出现一个新的edge，则可以满足此需求，否则不行
【安全状态】系统按照一定顺序为每个进程分配资源同时避免死锁
：：能够找到一个序列使得当前的空闲资源和次序列之前的所有持有的资源加起来（能够释放出的资源）>当前进程需要的资源，则系统处于安全状态
- 处于安全状态就一定不会有死锁
【银行家算法】检查如果分配了这个资源，之后系统是否仍然处于安全状态，如果是的话就可以分配，否则不给分配
